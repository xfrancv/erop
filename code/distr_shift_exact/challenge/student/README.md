# Starter code — *Know what you don't know under a new prior*

Everything here is optional: the competition data already contains
`predictions.csv` and `sample_submission.csv`, so you can work straight from the
CSV files. The kit exists so you can see how the baseline was built and — the
useful part — **score yourself offline** before spending a submission.

## The task in one paragraph

You get batches of images, described by the base predictor's calibrated
posterior `p_tr(y | x)` rather than by pixels. Every batch was drawn under one
unknown label prior `θ*`, taken from the 8 priors in `test_priors.csv`. That
posterior is under the **training** prior, which is not one of the 8 — so it is
wrong for every batch, and the batch itself is your only evidence about which of
the 8 applies. For each image you submit a label and a confidence. The organiser
pools all images of the same batch size, sorts by descending confidence, keeps
the most confident 80 %, and measures how much worse your labels are than a
reference predictor that was told each batch's true prior. Lower is better.
Negative is possible.

## Files

| File | What it is |
| :-- | :-- |
| `make_sample_submission.py` | builds the baseline submission — and shows the format |
| `metric.py` | the competition metric, the same code the leaderboard runs |
| `evaluate.py` | scores a submission against `dev_solution.csv` |

## Install

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

numpy and pandas are all you need; matplotlib only for `evaluate.py --plot`.
There are no images to decode and no network to run, so there is no deep-learning
dependency. On a Kaggle notebook everything is preinstalled — install nothing.

## Use

Set `DATA` to wherever the competition data lives:

```bash
DATA=../competition-data          # or /kaggle/input/know-what-you-dont-know-under-a-new-prior
```

**1. Build a baseline submission and score it.** Start here — it takes seconds
and proves the whole loop works:

```bash
python make_sample_submission.py --data-dir $DATA \
    --batches dev_test_batches.csv --out dev_sample_submission.csv
python evaluate.py dev_sample_submission.csv $DATA/dev_solution.csv
```

You should see a per-batch-size table and one number at the bottom. That number
is what the leaderboard would give this baseline on those rows. Beating it is
the competition.

**2. Score your own predictor.** Write a `submission.csv` with the three columns
`row_id`, `pred`, `confidence` for every row of `dev_test_batches.csv`, then:

```bash
python evaluate.py my_submission.csv $DATA/dev_solution.csv --plot
```

**3. Submit to Kaggle.** Same predictor, run on `test_batches.csv` instead:

```bash
python make_sample_submission.py --data-dir $DATA \
    --batches test_batches.csv --out submission.csv
```

## Scoring yourself: what you can and cannot do

The competition data contains **two** sets of batches:

* `test_batches.csv` — the real test set. You submit predictions for these. The
  labels are not in the data, so you cannot score yourself on them.
* `dev_test_batches.csv` — batches built from the development images, whose
  labels you *do* have (`dev.csv`). `dev_solution.csv` gives the ground truth
  and the reference predictor's answers, so `evaluate.py` scores you exactly as
  the leaderboard would.

Both were generated by the same procedure, so a predictor that improves on the
development benchmark should improve on the leaderboard. The development set is
smaller, so its numbers are noisier — do not read small differences as real.

## How the files join up

Everything is keyed on `row_id`, one row per test image:

* `test_batches.csv` — which batch each `row_id` belongs to (`id_test`).
* `predictions.csv` — the eight class probabilities for each `row_id`.
* `dev_test_batches.csv` / `dev_predictions.csv` — the same pair for the
  development benchmark.
* `dev.csv` — the labeled development pool: a `label` and the same eight
  probabilities. Use it to fit or recalibrate anything you like.

Rows sharing an `id_test` were drawn under the same unknown prior. **Rows in
different batches are independent** — see the competition rules on what you may
not do with them.

## Four things that cost people points

**The confidence column is a ranking, not a probability.** Any strictly
increasing transformation of it gives exactly the same score. What it has to do
is put your *likely-wrong* predictions at the bottom.

**Confidences are pooled across batches.** Within one batch size, every image
from every batch goes into one ranking. So a batch whose prior you could not
pin down should carry uniformly *lower* confidence than one you could.
Normalising confidences within a batch throws that information away.

**Ties are broken by ascending `row_id`.** A constant confidence column is
scored deterministically, and badly.

**You are not asked to reject anything.** Submit a label for every row; the
organiser sweeps the coverage. There is no way to abstain in the file format.
